# Auto Applier

A Chrome extension (Manifest V3) that autofills job applications from a saved profile. Built for the user and one friend (5 users at most), not for the public. There is no backend: everything runs in the browser and data stays local. It is also an LLD design practice project, so how it is built matters as much as what it does.

## How we work (read this first)

- **The user proposes the design; Claude assists.** Do not redesign things or offer a competing architecture. Answer questions, point out problems, and build what was agreed.
- **One step at a time.** After each step: show the diff in the chat message itself (the user cannot see tool output), list the choices made, then wait for approval. Commit only when the user says "commit", then start the next step.
- **Tests first (TDD).** Write the test, run it and see it fail for the right reason, then implement, then run tests, `npm run typecheck` and `npm run build`.
- **Be honest about what is not verified.** The popup and content script were checked by hand in Chrome on `fixtures/simple-application.html` only (saving a profile, filling, outlining the fields that need the user). They have not been tried on a real job site. Say so rather than implying more was tested.
- **Do not guess.** If this file does not answer a design question, ask. Do not invent files, keys or behavior.
- Ask at most one or two blocking questions. Pick sensible defaults, state them, and let the user correct them.

## Code style

- Readable code. One comment line above every function saying what it does, and one comment line at the top of every file saying what the file does. No other comments unless truly needed. (JSON files cannot have comments.)
- TypeScript, strict. String-literal unions instead of enums. Types for data, interfaces for behavior.
- Immutable: build new objects, do not mutate. Small files, one clear job each.
- No `console.log`. Never use `innerHTML` with dynamic data (use `textContent`).
- Zod only at the edges (validate untrusted data). `types.ts` stays the source of truth for the `Profile` shape.
- Commit messages: `<type>: <description>` (feat, fix, refactor, docs, test, chore). No Co-Authored-By trailer (the user disabled attribution).

## Repo and commands

- This folder has its **own git repo** (branch `main`). The user's home folder is a separate repo, so never commit from there.
- npm workspaces. Tools: TypeScript, **esbuild** (bundler, chosen over Vite because content scripts must be single files), Vitest 5 (needs `vite` installed), jsdom (DOM tests), `@types/node` (for tests that read files), Zod 4 via `zod/mini`.
- `npm test` runs the core tests and then the extension tests (those stub the `chrome` global with `vi.stubGlobal`). `npm run typecheck` checks both packages. `npm run build` writes `packages/extension/dist`.
- Load in Chrome: `chrome://extensions` → Developer mode → Load unpacked → `packages/extension/dist`. After changes: build, then reload the extension.
- DOM tests need `// @vitest-environment jsdom` on the second line of the test file (after the header comment).
- Do not `cd` into `node_modules` and leave the shell there.
- TypeScript 7 loads no `@types/*` unless the tsconfig lists them: core's tsconfig has `types: ["node"]`, the extension's has `["chrome", "node"]`.
- **Bundle size matters.** The content script is injected into every frame of every page. Import Zod only as `import * as z from "zod/mini"` plus `import en from "zod/v4/locales/en.js"` (the `.js` is required). A plain `import { z } from "zod"` pulls in every language and made `content.js` 820 KB; it is now about 70 KB. Check `ls -l packages/extension/dist` after adding any dependency.
- jsdom replaces the global `URL`, so tests read files with `join(import.meta.dirname, ...)`, not `new URL(..., import.meta.url)`.
- **pdf.js (`pdfjs-dist` 6.x):** import it only from popup code (about 435 KB minified; its worker `pdf.worker.min.mjs` is a separate 1.27 MB file loaded only when a PDF is read). Cleanup is `loadingTask.destroy()`; the document object has no `destroy`. PDFs that use standard fonts without embedding them need `standardFontDataUrl` pointing at the package's `standard_fonts/` folder (816 KB). The CJK `cmaps/` folder (1.6 MB) is not shipped, so Chinese, Japanese and Korean resumes will read poorly. `createPdfTextReader` takes the library as an argument and is tested against the legacy build in Node; it is cast to a structural `PdfLibrary` type, so check the real types in `node_modules/pdfjs-dist/types` when changing it.
- To try the extension by hand: `python3 -m http.server 8000 -d fixtures`, open `http://localhost:8000/simple-application.html`, save a profile in the popup, press "Fill this page".
- The Claude-in-Chrome tool cannot open `chrome-extension://` pages, so the popup, settings and resume upload can only be checked in a real browser by the user. The ID of the unpacked `dist` folder comes from its path (currently `gpgnddaahdhncomocgljcnfdfnoaoclf`).

## The pipeline (target design)

`fillPage(root, profile, setup = DEFAULT_SETUP)` runs: discover → match → resolve → fill → report, one field at a time in page order (sequential, because comboboxes need focus). `DEFAULT_SETUP` is the matcher chain plus the five fillers; tests and adapters can pass their own.

1. **discoverFields(root)** (radios and checkboxes that share a name and form become ONE field each: `radio` or `checkbox-group`, labelled by the fieldset legend or group label, with each box's label as an option; a lone checkbox stays `checkbox`) skips disabled and `aria-hidden="true"` controls (React-select adds invisible helper inputs like that) and returns `FormField[]` (element, kind, label, name, options, groupId). Radio groups are ONE field (first radio is `element`, `options` are each radio's label, `groupId` is the radio name).
2. **Matcher chain** `matchField(field, matchers, threshold = 0.8)`: first result with confidence >= threshold wins (inclusive), otherwise `null`.
   - `AttributeMatcher`: autocomplete attribute 0.95, label 0.85, name attribute 0.80. Specific rules come before generic ones (legal/preferred/middle before first/last). Text-only keys (names, email, phone, links) do not match select or radio fields.
   - `BareNameMatcher(fields)`: maps a bare "Name" to `fullName`, but only when no other field on the page is a first or last name. Built per page, so the chain is `[new AttributeMatcher(), new BareNameMatcher(fields)]`.
   - The confidence numbers are the assistant's picks and are easy to retune in `matching/constants.ts`.
3. **resolveValue(profile, key)** returns the text to type, or `undefined` if the profile has none (then the field is flagged, not filled). Derived keys: `fullName`, `legalName` (falls back to full name), `preferredName` (falls back to first name). Booleans become "Yes"/"No". Empty skills → `undefined`.
4. **Validating the value against the field** happens inside each filler (option matching, read-back after filling), not as a separate step. It is not Zod.
5. **Fillers** (one per field kind, behind the `Filler` interface): `canFill(field)` and `fill(field, value)` returning `filled`, `skipped{reason}` or `failed{reason}`.
   - `TextFiller` never overwrites a different existing value (skips with a reason), skips read-only or disabled fields, and reads the value back to catch silent rejection (a phone number the page reformatted, for example `(555) 123-4567`, with seven or more digits matching, counts as filled). It fires only `input` and `change` events (no focus or blur).
   - `setNativeValue` uses the prototype's native value setter, then dispatches `input` and `change`, so React-style forms notice.
6. **Report**: `FieldReport { field, profileKey?, outcome }`. The outcome is a `FillResult` (`filled`, `skipped`, `failed`), or `unmatched` (no matcher result), or `no-value` (key matched, profile has nothing). `needsAttention` means failed, unmatched or no-value; those fields are outlined on the page (red for failed, amber for the rest), and fields the AI wrote or chose (`needsReview`) are outlined blue. The popup button sends `fill-page` to every frame of the tab; each frame validates the saved profile (`validateProfile`), runs `runFill` on its own document (`extension/src/fill/runFill.ts`: `fillPageWithAssistant` through `BackgroundLLMClient`, with the page's title, description and main text as `jobContext`) and sends a `fill-result` (summary plus notes) to the background worker, which saves it in `chrome.storage.session` under the tab and frame (`ChromeSessionFillStore`). The popup writes a "running" marker when Fill is pressed (clearing the tab's old results), then shows whatever is saved for the tab: it adds the frames up (`combineResults`) and shows `Filled N · Left alone N · Needs you N` (plus `· Check the AI's work on N`) and the AI notes, each once, or "Filling…" while nothing has arrived. Because the worker keeps the results, reopening the popup shows the last result, and a result that arrives after the popup closed is not lost. Saved results are dropped when the tab's top frame loads a new page (`page-loaded`); same-page navigation in a single-page app does not clear them.
7. **Stop before submit.** The user has not answered whether it should auto-submit. Default: it stops and the user reviews and submits. Do not build auto-submit without asking.

## Profile model

`Profile` = `personal` (names, email, phone, links), `experience[]`, `education[]`, `skills[]`, `answers`, `resume?`.
- `personal` has optional `middleName`, `legalName`, `preferredName`; `links` has optional `linkedin`, `github`, `portfolio`.
- `answers` = `workAuthorization` (status text such as "Citizen"), `isAuthorizedToWork` (boolean, for the yes/no "authorized to work?" question), `needsSponsorship` (boolean), optional `noticePeriod`, `salaryExpectation`. Do not merge `workAuthorization` and `isAuthorizedToWork`: they answer different questions.
- `PROFILE_KEYS` in `profile/keys.ts` is the single list of matchable keys. `resolveValue` uses a `Record<ProfileKey, ...>`, so adding a key forces adding its resolver.
- `validateProfile(input: unknown)` returns `{ ok: true, profile } | { ok: false, errors: ["personal.email: ..."] }`. It takes an already-parsed object (not JSON text) and strips unknown keys. Dates are plain non-empty strings and links are not URL-checked on purpose.
- The popup form (`ProfileForm`) covers personal info, links, skills, answers. `fromFormValues(values, existing)` keeps `experience`, `education` and `resume` from the existing profile. Experience/education have no editor yet.
- The resume file itself is binary and goes in IndexedDB; `Profile.resume` only holds a pointer (`storageKey`).

## LLM design (not built yet)

- The LLM sits behind `LLMClient.completeJson(prompt): Promise<unknown>`; one implementation per provider. **Provider: Google Gemini (chosen by the user).** `GeminiLLMClient` (`core/src/llm`) calls `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent` with the key in the `x-goog-api-key` header (never in the URL) and `generationConfig.responseMimeType: "application/json"`; the answer text is `candidates[0].content.parts[].text`. Google's newer Interactions API (`/v1beta/interactions`, needs an `Api-Revision` header) exists and its quickstart now leads with it. `generateContent` was chosen because its response format is documented in the API reference and the endpoint is live (a keyless request returns 403, not 404). If it is ever retired, write a second client behind `LLMClient`. The default model is `gemini-3.1-flash-lite`, chosen by the user as a cheap stable model (Google's models page lists it as stable, and `gemini-3.5-flash-lite` as the other stable lite option). The name came from that page and has NOT yet been confirmed with a real call; it is a user setting in the popup. The user supplies their own API key. It is stored in plain text in `chrome.storage.local` under `llm-settings`; only the popup (to save it) and the background worker (to use it) read it, never the content script. Popup and content code reach the LLM through `BackgroundLLMClient`, which messages the worker; the worker ignores messages from other senders.
- **Backup provider (Groq), added after Gemini returned a 503.** `GroqLLMClient` calls `POST https://api.groq.com/openai/v1/chat/completions` (Bearer key, `response_format: {type: "json_object"}`, answer in `choices[0].message.content`). `FallbackLLMClient` tries clients in order and returns the first answer; if all fail it throws every reason joined with "; " (one client: its own error unchanged). Settings are per provider (`ProviderSettings = { gemini?, groq? }` under the same `llm-settings` key; the old single `{apiKey, model}` shape is read as Gemini's). `PROVIDER_ORDER` (Gemini first, Groq backup) is the one place the order lives; `createFallbackClient` builds the chain from the providers that have a key. Any failure of one provider moves on to the next, including a bad key. A request may name one provider (Test connection does), which then runs alone with no fallback. **Retries:** each provider's client is wrapped in `RetryingLLMClient`, which waits 1 s then 3 s and tries again, only when the client threw an `LLMRequestError` with `retryable: true` (HTTP 429, 500, 502, 503, 504, or a dropped connection such as "Failed to fetch"). A timeout, a bad key, a missing model (404), a blocked prompt or an unusable answer is not retried. Retrying happens before falling back to the next provider. The default Groq model `llama-3.1-8b-instant` (the user's choice) is from Groq's production model list and has NOT been confirmed with a real call or for JSON mode; an 8B model may parse resumes less accurately than a larger one. The same prompts go to whichever provider answers, so resume text and profile slices can reach Groq too. Groq was never called for real: it is tested with a fake network only.
- All LLM calls run in the background service worker, never in the content script (keeps the key away from page scripts). Content script and popup talk to it through typed messages.
- **Resume parsing:** extract text with plain code (pdf.js), then the LLM turns the text into JSON, then `parseResume` (`core/src/resume`) checks the answer with a lenient Zod schema and cleans it into a `ProfileDraft` plus `warnings`. Defaults chosen by the assistant (not yet confirmed by the user): never invent, so unknown stays blank; a job or degree missing required details is dropped with a warning, and a missing start date falls back to the end date; "Present" end dates are left out; skills are de-duplicated; text over 50,000 characters is cut with a warning. The prompt marks the resume text as untrusted. `applyDraftToFormValues` fills the form fields the draft has values for and never touches the answers. **After parsing, the profile is saved automatically when it is valid (the user's decision).** `buildProfileFromDraft(draft, currentFormValues, existingProfile)` applies the draft to the form values, takes the draft's jobs and degrees over the saved ones (keeping the saved ones when the draft has none), keeps the saved resume pointer and answers, and returns a `ValidationResult`. If valid, the popup saves it and refreshes the form. If not (usually a first run, because work authorization is a required answer a resume cannot supply), the popup fills the form with the draft and lists the errors for the user to fix and Save. The user can edit and Save again at any time, and a later upload updates the same profile. Experience and education have no editor yet (step 2b), so step 9b shows them read-only. Scanned image PDFs have no text and will not work. Only PDF (and plain text) are planned first; DOCX is undecided.
- **Ambiguity goes to the LLM (decided by the user), in ONE call with the whole profile (the user's decision, Nov 2026, replacing an earlier three-call design that sent no personal values).** `fillPageWithAssistant(root, profile, llm, { setup?, jobContext? })` (`core/src/assist`) runs `fillPage` first (rules only), then makes a single call for every **leftover** field: outcome `unmatched`, `no-value`, or `failed` with code `no-option-match` or `no-options` (a dropdown that listed nothing for what the rules typed). Eligible kinds: text, select, radio, checkbox-group and combobox, only when something can fill the field, it has a label or name, and (for text) the user has not typed in it. **Never asked about:** single checkboxes (consents such as "I agree" are never ticked by the AI), file uploads, dropdowns that failed for another reason (for example the page did not accept the pick), and anything past the first 40 fields. **Dropdown options are read first:** a combobox's choices exist only once it is open, so before building the prompt each leftover combobox is opened with a click (`ComboboxFiller.readOptions`, found through the `OptionReader` interface), its option texts are read (for a dropdown whose profile value is known, the options a search for that value finds come first), and the list is closed with Escape; the model then picks one of the real options (checked like a select's). A list that stays empty (a search box before typing) is asked as free text. Checked by hand on Stripe's Greenhouse form with the real fillers and a scripted stand-in for the model: the residence-country, remote, earlier-employment, WhatsApp, gender, Hispanic and veteran dropdowns all took a real option. Not run with real Gemini.
  - **What is sent** (`answerFieldsPrompt.ts`): the rules (page text is untrusted, never invent, copy options exactly, equal-opportunity handling, yes/no from notes), the applicant's WHOLE profile as JSON (name, contact details, links, jobs with descriptions cut to 500 characters, education, skills, answers including salary, and `notes`; only the resume file pointer is dropped), the job page text (title, description and main text, cut to 4,000 characters) only when a written question is among the fields, and the fields (id, label cut to 300 characters, kind, up to 60 options each cut to 100 characters, `longAnswer` mark). Never the API keys.
  - **What comes back:** `{ "answers": [ { "id", "answer" } ] }`. `parseFieldAnswers` (`zod/mini`) drops blank answers, unknown ids and repeats, cuts answers to 2,000 characters, and for select, radio and checkbox-group fields accepts only an answer that equals one of the options (matched ignoring case and spacing, returned exactly as the page spells it). A wrong shape throws the shared `FORMAT_ERROR`.
  - **Filling:** each answer goes through `fillWith`. A filled field is reported `filled` with `source: "ai"` (outlined blue to check; every outlined field also carries `data-auto-applier` (failed, unmatched, no-value, review) and `data-auto-applier-reason` (a sentence from `explainReport`, such as "Failed: No single option matches …" or "Not recognised by the rules. The AI was asked and left it blank."), so a person can read why from the page), a written question (`isFreeTextQuestion`: a textarea, or a label ending in "?" or with six or more words) as `drafted`. A fill that fails keeps its failure outcome. A field the model leaves out stays as the rules left it.
  - **Equal-opportunity and yes/no questions** (gender, ethnicity, veteran or disability status) are answered from the profile's free-text `notes`; "ever employed by <company>" is answered from the jobs list (not listed → No), opt-ins to messages default to No, and work-style preferences (remote, hybrid, on-site) come only from the notes ("Other facts the AI may use" in the popup); if the notes do not say, the prompt tells the model to choose a "decline to answer" option when offered, else leave the field out.
  - **A failure stops the step** and adds the note `AI help skipped: <reason>`; what the rules filled is kept. Fewer calls than before means fewer retries and one failure point instead of three. Rough cost: about 4,000 tokens in and under 1,000 out per page that has leftovers.
  - **What leaves the browser on "Fill this page"** (only when the rules left something undecided): your whole profile, the unresolved fields' labels and options, and sometimes 4,000 characters of the job page. It goes to Gemini, and to Groq if Gemini failed. Nothing is sent when the rules fill everything. Without an API key the popup shows "AI help skipped: No LLM is set up…" on every fill, and a page inside an iframe only sees its own frame's text. Not run against real Gemini yet.
- Never send credentials, the vault or the API key to the LLM.

## Known gaps and open decisions

- Auto-submit vs stop-before-submit not confirmed (default: stop).
- Labels are matched with English patterns only.
- A radio group whose first radio is disabled is not discovered at all (`discoverFields` describes a group from its first radio). Not fixed; fix it if it shows up on a real site.
- A select with no placeholder: an untouched first option is treated as empty and gets overwritten; an option the page marked `selected` is respected.
- **Fields that are skipped:** text, select and combobox fields the browser says are not rendered (`checkVisibility`, used only where the browser has it, so jsdom treats everything as visible); `aria-hidden="true"` controls; `type=search`; anything inside a footer, nav, header or `contentinfo`/`navigation`/`banner`/`search` landmark; and newsletter or subscription signups (a word like newsletter or subscribe in the control's name, or in an id or class within six ancestors). Checkboxes, radios and file inputs are kept even when hidden, because pages hide them behind styled controls. Fields hidden off-screen (not `display: none`) are still not caught, so some honeypots would be filled.
- Every unmatched field is outlined amber, including search boxes and cookie checkboxes; this may be noisy on real pages.
- **Resume upload (`FileFiller`)**: the `resume` key (matched on a file input labelled Resume, CV or Curriculum Vitae, or named or id'd that way, because Greenhouse labels both uploads just "Attach") resolves to the saved resume's file name, so the field reports "no value" when no resume is saved. `FileFiller` is not in `DEFAULT_SETUP` because it needs a way to load the file: `runFill` adds it with `loadResumeFromBackground`. The file is in IndexedDB on the extension's origin, which a page's script cannot read, so the content script sends `get-resume` to the background worker, which replies with the name, type and bytes as base64 (`resume/base64.ts`, because runtime messages cannot carry binary). The filler refuses an input whose `accept` does not allow the file, skips an input that already has a file, builds a `File`, assigns it through a `DataTransfer`, fires `input` and `change`, and checks the input took it. A cover letter upload is not matched. This has not been tried in real Chrome: jsdom cannot assign `input.files`, so the assignment itself is only tested with a fake.
- **React-select dropdowns on Greenhouse (found on Stripe's real form, Nov 2026) only open for a complete click.** A bare `mousedown`, an Arrow Down `keydown`, `execCommand("insertText")`, `element.click()` and pointerdown plus mousedown all left `aria-expanded="false"`. What worked, tested on the real form in a browser tab: `pointerdown`, `mousedown`, `input.focus()`, `pointerup`, `mouseup`, `click` on the input, each with the element's centre as the pointer position, `button: 0`, `buttons` 1 on down and 0 on up, `detail: 1`, `composed: true` (no `view`). The same sequence on an option picks it, and once the list is open, typing filters it (School is a search that fetches options). `clickLikeUser` (`filling/events.ts`) now sends exactly that, and `ComboboxFiller` clicks the input first when `aria-expanded` is not "true", then types, then clicks the option. These were checked by hand in a test tab, not through the extension itself in real Chrome. `ComboboxFiller` also skips a dropdown that already displays a choice (it looks for a `single-value` or `singleValue` element within three levels of the input, because React-select keeps the input empty), counting it as filled when the shown text matches the wanted value.
- That form's first "Country" box is a phone country picker (intl-tel-input) with 244 always-present options written like `United States+1`. `ComboboxFiller.findOptions` now ignores options inside `[hidden]` and options in a list another combobox owns when its own list has not been announced yet (before, it read all 244 phone options for every other dropdown), and `optionText` drops a trailing dial code so "United States" matches "United States+1".
- **Search-backed dropdowns (School on Greenhouse): shorter searches, then "Other".** Stripe's School box filters by literal text, so "Indiana University Bloomington" finds nothing while the page lists "Indiana University - Bloomington" (checked live: "Indiana Univ" returned 9 options, "PES" returned "PES University"). `ComboboxFiller.fill` therefore types the value, and when no option matches it types the same words with the last one dropped each time (`shorterQueries`: "Indiana University Bloomington" → "Indiana University" → "Indiana", never under 3 characters; retries wait 700 ms at most) and matches each result list against the full value (punctuation ignored, so the hyphen no longer matters). It reports `no-options` when no search showed anything and `no-option-match` when some did. If an education dropdown (`school`, `degree`, `fieldOfStudy`) whose profile HAS a value is still unmatched after the AI step (or when that step failed), `fillPageWithAssistant` picks "Other" through the same filler and reports it `filled` with `source: "fallback"` (blue, "Picked 'Other': nothing in the list matched", counted with the AI's work); it is never done for other dropdowns, nor when the profile has no value. Checked live on Stripe's form with the real filler: the Indiana school filled as "Indiana University - Bloomington" in about 2 s, an invented school ended as "Other" in about 4 s. Not run through the extension itself.
- Not handled yet: shadow DOM, custom dropdowns that are not `input[role=combobox]`, password fields (skipped; they return with the login feature).
- `currentCompany`, `currentTitle`, `school`, `degree` and `fieldOfStudy` are derived, not stored: `profile/history.ts` picks the first job (or education) with no end date, else the first in the list (resumes list the newest first; dates are free text so they are not compared). They match labels like "Current or previous employer", "Job title", "School", "Degree", "Field of study" (school, degree and field also accept selects and comboboxes; employer and title accept text only). A bare "Title" or "Position you are applying for" is deliberately not matched. **Location** (step 12b): `personal` has optional `city`, `state`, `country` (typed in the popup form, or read from the top of the resume: the resume prompt asks for them and fills the country only if the resume names one; a resume's location replaces what is in the form only where the resume has a value). Keys `city`, `state`, `country` and a derived `location` ("City, State, Country", unset parts left out, in `profile/location.ts`). Rules sit at the end of the list so words like "state your notice period" hit the earlier rule first: both city and state in one label → `location`; "city" → `city`; state, province or region → `state`; "country" (not "country of citizenship/birth/origin", not "country code") → `country`; a label starting with "location" or "Where are you based" → `location` (text and combobox only). Autocomplete `address-level2`, `address-level1`, `country`, `country-name` map too. "Preferred work location" and "Office location" are deliberately not matched.
- A profile saved before `isAuthorizedToWork` existed will show "No" for it in the form. The user was told to re-check it and save.
- Making a form field fail on a real site is expected; the `FillResult` must say so instead of failing silently.

## Handling sites that resist an extension

Content scripts cannot be blocked by a site's CSP. What actually breaks, and the plan:
- Forms in iframes: `all_frames: true` plus host permissions (already in the manifest).
- Shadow DOM: `chrome.dom.openOrClosedShadowRoot`.
- Frameworks ignoring `el.value = x`: `setNativeValue` (done).
- Custom dropdowns: `ComboboxFiller` (click, type, pick the option).
- File upload: build a `DataTransfer` and assign `input.files`.
- Sites checking `event.isTrusted` (rare): last resort `chrome.debugger`, which shows a banner.
- `chrome://` pages and the Web Store cannot run extensions at all (not a problem for job sites).

## Future (do not build early, keep the seams open)

Open for extension, closed for modification: new behavior is a new class behind an existing interface. Planned later, each as a plug-in:
- New sites → new `SiteAdapter`. New matching rules → a new `Matcher` in the chain. New input kinds → a new `Filler`.
- Job scraping or RAG → a `JobSource` interface. Tailored resumes → a `ResumeProvider` (today: the one uploaded file). Email verification codes → a `VerificationCodeProvider` (today: the user types the code).
- Autonomous applying runs headless and reuses `packages/core`. It keeps a human approval step for submit at first.
- A backend would swap the `ProfileStore` and `LLMClient` implementations. Only build the interfaces a step actually uses (YAGNI).
- The user's friend runs their own copy: clone, build, load unpacked, use their own API key and profile. Secrets and personal data never go in the repo.
